NAME

graphs.cfg - Configuration of the showgraph CGI

 

SYNOPSIS

$XYMONHOME/etc/graphs.cfg

 

DESCRIPTION

showgraph.cgi(1) uses the configuration file $XYMONHOME/etc/graphs.cfg to build graphs from the RRD files collected by Xymon.

 

VOCABULARY

Four terms are used consistently in this page and in the keywords below:

metric
one measured quantity (one DS: line of an RRD) - the curves drawn on an image.
instance
one measured object (a filesystem, a disk, an interface) - one RRD file. Instances are what filters match, counts count, and paging slices.
graph
one [section] definition in this file.
image
one rendered picture (a paging slice). MAXINSTANCESPERIMAGE instances fill one image.

Historical names are kept as frozen aliases and documented against these terms: the third field of a GRAPHS environment entry ("name:partname:N", internally "maxgraphs") is the historical spelling of MAXINSTANCESPERIMAGE; the "<!-- linecount=N -->" status hint is the historical spelling of an instance count.

 

FILE FORMAT

Each definition of a graph type begins with a "[SERVICE]" indicator, this is the name passed as the "service" parameter to showgraph.cgi(1). If the service name passed to showgraph.cgi is not found, it will attempt to match the service name to a graph via the TEST2RRD environment variable. So calling showgraph.cgi with "service=cpu" or "service=la" will end up producing the same graph.

A graph definition needs to have a TITLE and a YAXIS setting. (The X-axis is always time-based).

A definition may also carry "MAXINSTANCESPERIMAGE N": how many of the matched RRD files are drawn per image when a status or trends page splits this graph. This keeps the split size with the graph it describes; it overrides the legacy "name::N" suffix in the GRAPHS environment variable (see xymonserver.cfg(5)), which remains supported.

"EXSTOREPATTERN <regex>" and "STOREPATTERN <regex>" filter which instances are stored at all, for every writer path targeting this graph's files: instances matching EXSTOREPATTERN are never written, and when STOREPATTERN is set only matching instances are. Patterns are matched (unanchored, so a substring hit counts - anchor with "^" and "$" for a whole-name match) against the RRD filename minus its ".rrd" suffix, case-insensitively. Note this differs from FNPATTERN/ EXFNPATTERN, which match the full name including ".rrd". A graph with storage filters has a file set that diverges from what a status message shows, so a message-derived paging count cannot be trusted: the count comes from the fileset index instead, with an unsliced render only when no index is reachable. (These keywords replace the drafted RRDEXCLUDE/RRDINCLUDE environment variables; analysis.cfg's "DISK ... IGNORE" remains the tool when the status line should disappear too.)

Writer-side keywords (EXSTOREPATTERN, STOREPATTERN) are read once at xymond_rrd startup, so a change to them takes effect only after xymond_rrd is restarted; the presentation keywords are re-read by the CGIs on every page request.

An "EXSTALEPATTERN <regex>" keyword exempts matching instances from staleness. The freshness window itself is one fixed number - 86400 seconds (one day), main's historic value: RRD files older than that are hidden from graphs requested with showgraph.cgi's "nostale" option - the graph links Xymon's own pages generate always pass it; a hand-written URL without it shows every file - and the writer-kept fileset index applies the same window to its paging counts, so the count always equals what renders. Instances the pattern matches are NEVER considered stale: they always render and always count. Use it for legitimately periodic instances - a weekly backup mount, a monthly job - whose graph must stay visible between appearances (e.g. "EXSTALEPATTERN backup"). The pattern is matched like the storage patterns (against the filename minus its ".rrd" suffix, case-insensitively, unanchored). An exempted instance that is truly gone stays visible until its RRD file is deleted - the file is easy to spot, its mtime stops moving. Note the window has a practical floor: freshness advances only as fast as the update cache writes (up to ~1h behind), which the fixed one-day window absorbs.

A "GRAPHOPTIONS <options>" keyword passes extra rrdtool graph options for this graph. When set it REPLACES the global RRDGRAPHOPTS environment (see xymonserver.cfg(5)) for this graph - the two are not combined. Static Y-range options placed here (-u/-l, --upper-limit/--lower-limit) are dropped whenever the viewer supplies a range - the zoom feature - so a zoom box always wins; prefer declaring fixed ranges only where zooming that graph is pointless.

A "THRESHOLDS OFF" keyword suppresses the automatic co-plot of threshold relations a self-describing METRICS block declared (see xymond_rrd(8)): the threshold curves and HRULEs disappear from the synthesized graph, while the threshold datasets still never plot as peer metrics. The default (no keyword, or "THRESHOLDS ON") co-plots on single-instance images. A section may carry only this keyword - the graph definition itself stays synthesized; a hand-written definition always has the last word.

A "TRENDS" keyword makes the graph a member of the trends-column page without an entry in the GRAPHS environment variable - the membership lives with the graph definition. Graphs listed in GRAPHS remain members as before.

"INCLUDE <name>" inherits an earlier-defined graph: its header keywords (TITLE, YAXIS, FNPATTERN, MAXINSTANCESPERIMAGE, TRENDS, ...) are copied, and its definition lines are copied in place. The variant's own keywords override the inherited ones, wherever they appear relative to the INCLUDE line, and its definition lines append - so a variant can retitle, retune the split size, or add curves without repeating the base. Two caveats: the base must be defined earlier in the file (a forward reference inherits nothing), and the keyword must be written in upper case - a lowercase "include" is the configuration reader's file-inclusion directive (include <filename>), processed before graphs are parsed:

[diskio_ops_wide]
INCLUDE diskio_ops
TITLE Disk operations (wide)
MAXINSTANCESPERIMAGE 5

TITLE
text shown as the title of the graph.
YAXIS
text shown as the YAXIS heading.

If a fixed set of RRD files are used for the graph, you just write those in the RRDtool definitions. Note that Xymon keeps all RRD files for a host in a separate directory per host, so you need not worry about the hostname being part of the RRD filename.

For graphs that use multiple RRD files as input:

FNPATTERN
a filename pattern.
EXFNPATTERN
optionally, a pattern of files to exclude from the graph (see "[tcp]" for an example).

When FNPATTERN is used, you can use

"@RRDFN@"
in the RRDtool definitions to pick up each filename.
"@RRDIDX@"
is an index (starting at 0) for each file in the set.
"@RRDPARAM@"
contains the first word extracted from the pattern of files (see e.g. "[memory]" how this is used).
"@COLOR@"
picks a new color for each graph automatically. Aggregate values across all files selected by FNPATTERN can be built with "@AVG:name@", "@SUM:name@", "@MIN:name@", "@MAX:name@", "@AVGNAN:name@", "@SUMNAN:name@", "@MINNAN:name@", "@MAXNAN:name@", "@COUNT:name@", "@MEDIAN:name@", "@STDEV:name@", "@PERCENT:name:pct@" and "@Ppct:name@" (short form, e.g. "@P95:name@" or "@P99.9:name@"). The "name" portion is the variable-name prefix used by preceding "DEF:name@RRDIDX@=..." lines -- the aggregate expands to "name0,name1,...,nameN-1" followed by the operator's RPN. "pct" is a decimal percentile (0-100, at most one dot). For example, after defining "DEF:t@RRDIDX@=@RRDFN@:ds0:AVERAGE", the line "CDEF:avg=@AVG:t@" expands to "CDEF:avg=t0,t1,+,t2,+,3,/" when three files are matched; "@P95:t@" expands to the matching RRDtool PERCENT RPN; "@PERCENT:t:99.9@" is the long form of "@P99.9:t@".

When the surrounding graph is sliced by "first"/"count" CGI parameters, the aggregates honour the slice: only the selected RRDs (firstidx through lastidx inclusive) contribute. An empty selection yields "UNKN" for arithmetic ops and "0" for "@COUNT:" (so dividing a "@SUMNAN:" by a "@COUNT:" stays safe on the empty set: 0/0 in RRDtool RPN is UNKN as well).

Semantics that rely on RRDtool's RPN operators (so they match what "rrdgraph_rpn(1)" describes): "@STDEV:" emits the *population* standard deviation (divides by N, not N-1). "@MEDIAN:" returns the lower middle value when N is even. "@AVG:" divides by the selected count, not the non-NaN count -- if any contributor is UNKN the result is UNKN; for a NaN-aware mean combine "@SUMNAN:" with "@COUNT:".

Names accept alphanumerics and underscore (and the inner ":" in the "@PERCENT:name:pct@" form). "@DSIDX@"/"@PREVDSIDX@"-style index tokens must NOT appear inside an aggregate operand -- they are not expanded recursively, and the aggregate parser stops at the first "@" when locating the operand terminator.

For graphs that repeat a similar line per data source within a single RRD file (e.g. ping1..pingN slots of a SmokePing-style RRD), use the "DSCOUNT N" directive together with the "@DSIDX@" token. At parse time, every def line containing "@DSIDX@" is expanded into N copies with @DSIDX@ replaced by 1..N. The companion "@PREVDSIDX@" token expands to (current index - 1); a line that uses it automatically loops 2..N to avoid producing an invalid "ping0" reference. To override the loop's lower bound for a specific line, prefix it with "@DSSTART:K@" - the prefix is stripped and K becomes the new lower bound. If DSCOUNT is omitted but @DSIDX@ is used, the count is read at render time from the actual RRD file, so a block doesn't need to repeat the count and hosts with different sample counts each get every band.

For a bundle viewed one service at a time (e.g. "tcp:conn"), FNPATTERN capture group 1 must be exactly the service component: showgraph uses it both as the legend (@RRDPARAM@) and to select the single service - see "[tcp]", where "^tcp.(.+).rrd" captures "conn" from tcp.conn.rrd.

To draw the total of a dataset across all matched files, define the per-file DEF and sum it with "@SUMNAN:" (unknown values count as 0; use "@SUM:" if one silent contributor should make the total unknown instead). Such a graph should render unsliced - a paged aggregate would show partial sums - so either give the entry no split size or have the status declare it with instances=all (see xymond_rrd(8) on self-describing statuses). Example - one curve with the total read rate across all disks:

[diskio_ops_total]
FNPATTERN ^diskio_ops\.(.+)\.rrd
TITLE Total disk operations
YAXIS Operations/sec
DEF:t@RRDIDX@=@RRDFN@:reads:AVERAGE
CDEF:rtotal=@SUMNAN:t@
LINE2:rtotal#00CC00:total reads

Alternatively "@STACKIT@" stacks the per-file curves, whose silhouette is also the sum while keeping each file's contribution visible.

The remainder of the lines in each definition are passed directly to the RRDtool rrd_graph() routine.

The following is an example of how the "la" (cpu) graph is defined. This is a simple definition that uses a single RRD-file, la.rrd:

[la]
        TITLE CPU Load
        YAXIS Load
        DEF:avg=la.rrd:la:AVERAGE
        CDEF:la=avg,100,/
        AREA:la#00CC00:CPU Load Average
        -u 1.0
        GPRINT:la:LAST: \: %5.1lf (cur)
        GPRINT:la:MAX: \: %5.1lf (max)
        GPRINT:la:MIN: \: %5.1lf (min)
        GPRINT:la:AVERAGE: \: %5.1lf (avg)\n

Here is an example of a graph that uses multiple RRD-files, determined automatically at run-time via the FNPATTERN setting. Note how it uses the @RRDIDX@ to define a unique RRD parameter per input-file, and the @COLOR@ and @RRDPARAM@ items to pick unique colors and a matching text for the graph legend:

[disk]
        FNPATTERN ^disk(.*).rrd
        TITLE Disk Utilization
        YAXIS % Full
        DEF:p@RRDIDX@=@RRDFN@:pct:AVERAGE
        LINE2:p@RRDIDX@#@COLOR@:@RRDPARAM@
        -u 100
        -l 0
        GPRINT:p@RRDIDX@:LAST: \: %5.1lf (cur)
        GPRINT:p@RRDIDX@:MAX: \: %5.1lf (max)
        GPRINT:p@RRDIDX@:MIN: \: %5.1lf (min)
        GPRINT:p@RRDIDX@:AVERAGE: \: %5.1lf (avg)\n

 

ADVANCED GRAPH TITLES

Normally the title of a graph is a static text defined in the graphs.cfg file. However, there may be situations where you want to use different titles for the same type of graph, e.g. if you are incorporating RRD files from MRTG into Xymon. In that case you can setup the TITLE definition so that it runs a custom script to determine the graph title. Like this:

	TITLE exec:/usr/local/bin/graphitle

The /usr/local/bin/graphtitle command is then called with the hostname, the graphtype, the period string, and all of the RRD files used as parameters. The script must generate one line of output, which is then used as the title of the graph. Each of the RRD pathname parameters will be enclosed in double quotes.

 

ENVIRONMENT

TEST2RRD
Maps service names to graph definitions.
